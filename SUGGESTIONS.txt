B12. Add a global query filter for Deleted (only if we do B11 option a)
    File: Data/AppDbContext.cs

    Why it matters: this is the standard EF Core way to do soft delete, and it
         means we never have to remember the filter in a controller again.

PART D - THINGS TO ASK THE SENIOR ABOUT (do not start these alone)
================================================================================

These are decisions, not fixes. Listing them so they are ready to discuss.

D1. The CV page is still public.
    ProfileController.cs Cv is marked [AllowAnonymous], so anyone can read any
    CV just by changing the id: /Profile/Cv/1, /Profile/Cv/2, ...
    Question: should a CV be public, or only visible to its owner and admins?
    If it should be shareable, a share token would be safer than
    guessable sequential ids.

D2. The image upload only checks the file extension.
    Services/ImageService.cs checks Path.GetExtension and nothing else, so a
    file named photo.jpg is accepted whatever is actually inside it. There is
    also no file size limit.
    Question: acceptable for an internal tool, or do we need a size cap and a
    real content-type check? I can implement either - I just need to know the
    limit we want.

D3. User deletion is permanent.
    Deleting a user removes the Identity account, their profiles, every related
    section, and the photo file from disk. No recycle bin.
    Question: acceptable, or do we want a soft delete for users too?

D4. Still no email confirmation or password reset.
    Anyone can register with any email address and there is no way to recover a
    forgotten password. This needs an email sender and probably a third-party
    service.
    Question: is this in scope at all? It is the biggest feature gap in the
    project but also needs infrastructure we may not have.

D5. Still no automated tests.
    Question: is a test project wanted now? I think xUnit plus
    WebApplicationFactory covering the five child controllers would be the most
    useful place to start, but I would rather have this agreed than start it
    and have it turn out we wanted a different approach.

PART E - IF I GET MORE TIME (bigger, self-directed work)
================================================================================

E1. Stop duplicating code in the five child controllers.
    AddressController, ContactController, EducationController,
    ExperienceController and SocialLinkController are near-identical: the same
    profile lookup, the same redirect guard, the same Create/Edit/Delete shape.
    That is roughly 1,200 lines with a lot of repetition.
    Option: a small base class or helper that resolves the current user's
    profile and applies the ownership check, leaving each controller with only
    its own field mapping.
    Caution: this is a refactor of working code. I would only do it after
            Parts B and C are merged and stable, and only with the senior's
            agreement. Doing it silently would be the wrong call.

E2. Check the admin list for N+1 queries.
    AdminController.cs projects City using
        City = x.Addresses.Where(a => a.IsPrimary).Select(a => a.City).FirstOrDefault()
    inside a Select over all persons. EF may translate this into one query, but
    it is worth confirming with logging switched on. If it is N+1 it will slow
    down as the table grows.
    Fix: verify with EF Core logging, then if needed use .Include or split it
         into two simple queries.

E3. Add a Languages section.
    A CV with languages listed is more complete. The pattern to copy already
    exists five times in the child controllers, so this is mostly repetition
    plus one migration.
    Note: Skills and Certifications were removed from this project earlier, so
          I should check before assuming languages are wanted either.

E4. Resize profile pictures before saving.
    ImageService stores the uploaded file as-is, so a 5MB phone photo is stored
    and served at full size on every page load.
    Fix: add thumbnail/resize logic in the service. Options are
    SixLabors.ImageSharp or System.Drawing (Windows only, so less portable).

E5. Profile photo security.
    The upload accepts any file that ends in an allowed extension and writes it
    into wwwroot, which means it is served straight back by the static file
    middleware. This links to D2 but is worth calling out separately because it
    is a file-upload path, not just a validation gap.
